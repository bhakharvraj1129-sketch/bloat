  How this works
  You build Bloat in 8 stages, from accounts to the app stores, in about 5 months to a paid
  launch (an estimate, not a promise). Claude Code writes the code; you decide, test on
  your phone and approve each step. Everything it builds comes from the master plan (Bloat
  Complete Master Plan v4.5) and its embedded data files.

     Who                                  Does

     You (product owner)                  Make decisions, keep the plan as the single source
                                          of truth, test every slice on a real phone, run the
                                          beta, talk to users

     Claude Code (builder)                Writes the code slice by slice, writes and runs the
                                          200 acceptance tests, fixes what fails, explains
                                          what it changed

     Claude (here)                        Designs the screens, updates the plan when you
                                          decide something new, reviews what was built
                                          against the plan

  Rules that prevent chaos
  Most failed builds with a coding agent fail the same few ways: the plan shifts mid-build,
  half-finished work piles up, or the agent quietly invents something. These rules close each
  of those.

     1. The plan is frozen during a slice. New ideas go on a "Later" list. Between slices, decide
        them here, update the master plan, then continue.
     2. One slice at a time, one part per session. A session ends with passing tests and a
          commit, or it is undone. Never leave work half-done overnight.

Bloat Build Guide

     3. Tests first. For each part, Claude Code writes the plan's acceptance tests before the
        code. A part without a passing test isn't done.
     4. Two memory files in the repository. PROGRESS.md (what is done, what is next) and
           DECISIONS.md (every choice made while building, with the date). Claude Code
          updates both at the end of every session and reads both at the start of the next, so
          nothing depends on its memory.
     5. Start every session the same way: "Read CLAUDE.md, PROGRESS.md and
        DECISIONS.md, then tell me what you will do today."
     6. No new libraries, tables, screens, wording or numbers without your yes. If it isn't in
          the plan or the decisions table, it asks.
     7. Database changes only move forward. Each change is a new migration file; an applied
          migration is never edited. Test project first, live project only at Gate 1.
     8. Two tries, then stop. If a fix fails twice, Claude Code stops and explains the problem in
        plain words; bring it here instead of letting it keep guessing.
     9. A save point after every slice. Tag the code ( slice-a-done , slice-b-done ) so you
          can always go back to the last working version.
   10. You test on real phones before saying "done". Passing tests show the rules work;
       only your hands show it feels right.

  Stage 0 — Accounts and tools (week 1)
  Set up these accounts before any code is written. All have free starts; paid plans begin
  around the beta. Costs are approximate and change; check each site.

          GitHub — where the code lives (free). Create a private repository called bloat .
          Claude Code — the builder. Comes with a paid Claude plan; install it on your computer
          and connect it to the GitHub repository.
          Supabase — create TWO projects: bloat-test (synthetic data only) and bloat-
          live (real users, from Gate 1). Free to start; about $25 a month once live.
          Vercel — connect the GitHub repository; every change gets a preview link. Free while
          building; the paid plan (about $20 a month) is needed for a commercial app.
          Anthropic Console (API) — create separate keys for test and live, and set a monthly
          spending limit in the account as the second safety net.
          Domain — buy it once the name is final (about $15 a year).
          Email sending (for sign-in codes and alerts), e.g. Resend — free tier to start.
          Error monitoring, e.g. Sentry — free tier to start; never send health data to it.
          Test phones — at least one iPhone and one Android phone, borrowed is fine. You test
          every slice on both.
          A password manager — store every key there, never in chats, documents or
          screenshots.

  Rule for keys: a secret key (Supabase service key, AI key) goes only into Vercel's
  environment settings. If one is ever pasted anywhere else, replace it the same day.

  Design comes before code, because changing a picture takes minutes and changing built
  screens takes days. The Bloat design system (colours, score scale, fonts, shapes, wording

        Decide the name question (keep "Bloat" or pick a more distinctive name) before the

        onboarding and dark mode on a design canvas with Claude: Today, Log bloating
          (bottom sheet), meal ingredient checklist, morning review, History, Possible triggers,
          Your journey, Upgrade, and the first onboarding screens. Each in light and dark.

  A slice is done only when all four are true:

     1. Every acceptance test for that slice passes automatically.

  bugs hide.

  How to work with Claude Code
  Claude Code is fast but literal: it builds what it is told, and fills gaps with guesses. Your job
  is to keep it on the plan.

  Set up once
     1. Put the master plan PDF and its three data files (questions, tests, configuration) in a
        docs folder in the repository. The data files are attached inside the PDF.

     2. Ask Claude Code to create a CLAUDE.md file at the top of the repository with Bloat's
          standing rules (it reads this file at the start of every session):

     Create CLAUDE.md with these standing rules for Bloat:
     - The single source of truth is docs/Bloat_Complete_Master_Plan_v4.5.pdf and
     the JSON files in docs/. Never change a rule, threshold, wording or price on
     your own; if something is unclear or seems wrong, stop and ask.
     - Build one slice at a time (plan section B06). Write the slice's acceptance
     tests first, then the code, then run all tests.
     - Wording: follow the README of the Bloat design system and plan A17. Never
     write "trigger found", "cause", "diagnose", "safe food" or "bad food".
     - Privacy: Row Level Security on every table; the two-user test must always
     pass; no health data in logs, analytics or error reports.
     - Secrets only in environment variables. Never print or commit keys.
     - Meals must always save, even when AI is off or limited.

  Every session (one part of a slice)
     1. Plan first. Ask it to plan before coding:

     We are building Slice A, part 1: sign-up, help page and consents.
     Read CLAUDE.md and the plan sections A07, A17 and screens 01-07.
     List the acceptance tests that cover this part, then propose a plan.
     Don't write code until I approve the plan.

     2. Approve or correct the plan. If it suggests anything not in the master plan, say no, or
          bring the question here so the plan is updated first.
     3. Build and test: "Approved. Build it, run all tests, and give me the preview link."
     4. Try it on your phone using the preview link. Note anything that looks or feels wrong.
     5. Fix: describe what you saw in plain words ("the Save button is hidden behind the
        keyboard on Android").
     6. Finish: "All good. Commit with a clear message and update the slice checklist."

  Your review checklist (every part)
          All tests pass, including the two-user privacy test
          Works on iPhone and Android, light and dark
          Looks like the approved design (colours, fonts, spacing, round shapes)
          Wording follows the rules; no medical claims

  How to test like a user: for one full week, use Bloat yourself every day exactly as a user
  would. Log real meals, forget to end an episode, skip a morning review, travel to another
  time zone if you can. Most real bugs show up here.

  Stage 5 — Early access and the 150-person beta (weeks 11–20)
  The beta is where the plan meets real behaviour. Pro is free for everyone in it; payments
  stay off.

     1. Early access (2 weeks). Invite 15–20 people you can reach easily. Watch the numbers
        below daily and fix anything that blocks logging.
     2. Beta (8 weeks). 150 adults with bloating at least weekly, 50 each from the US, Canada
        and India. Find them through the 25 discovery interviews, bloating and IBS
        communities (no spam), and friends of friends.
     3. Weekly routine during the beta: read the founder review queue, read feedback, look
          at the numbers, pick the top problem, fix it in one short Claude Code session.

     What to watch (privacy-safe, no health data)   Why it matters

     Onboarding finished                            Whether sign-up is too long

     Morning reviews done                           Whether the daily habit sticks

     Confirmed days per user                        Whether insights can ever appear

     Time to first possible trigger                 When people first get value

     Logging time per meal                          Whether logging is fast enough

     Still using in week 4 and week 8               Whether people stay

  Stage 7 — App Store and Google Play (after the paid launch)
  The same app goes into the stores, wrapped with Capacitor; no rebuild.

     1. Accounts: Apple Developer (yearly fee) and join the Small Business Program before
        the first sale; Google Play (one-time fee).
     2. Make it feel native, not like a website in a box. Apple rejects apps that are only a
        wrapped website. Use native touches: the phone's share sheet, haptics, the system
        keyboard behaving correctly, smooth back gestures, and saves that survive a lost
        connection.
     3. In-app subscriptions at the same prices as the web, through Apple's and Google's
        billing (a subscription service such as RevenueCat can handle both stores and the
        web in one place).
     4. Privacy forms: Apple's privacy labels and Google's data-safety form, matching the
        privacy policy exactly; health-app declarations where asked.
     5. Store listing: 5–6 screenshots that tell a story ("Log in 2 taps" → "See your patterns" →
        "Bring it to your doctor"), a short preview video, and wording from the plan: "a
        wellness tracker, not a medical device".
     6. Review notes for Apple and Google: explain that Bloat is a wellness diary, gives no
        diagnosis, quotes NHS guidance, and how to test the Pro features with a demo
        account.
